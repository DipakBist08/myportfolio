A good bug report lets a developer who was not there reproduce the bug on the first try. It has a specific title, numbered steps with the test data you used, separate expected and actual results, the exact environment, and evidence. Below is a complete bug report example, a template you can copy, and how the same fields map to Jira and Azure DevOps.

<KeyTakeaways>
- Write for someone who has never seen your screen and has five minutes to investigate.
- One action per step, with the exact test data you used.
- Keep expected and actual results separate, and quote error messages exactly.
- Severity is impact, priority is urgency. Propose severity; let triage set priority.
- Attach evidence, and remove passwords, tokens and personal data from it first.
</KeyTakeaways>

## What does a good bug report example look like?

Here is a complete report for a real-world kind of defect: a form that should reject empty input but submits anyway, in one browser only. Every field answers a question the developer would otherwise have to ask.

<BugReport
  id="QA-1042"
  title="Login: form submits with an empty email field, no validation error (Chrome)"
  severity="high"
  priority="P2"
  status="open"
  environment="Chrome 158.0 | Windows 11 | Staging, build 2.4.1"
  reportedBy="Dipak Bist"
  assignedTo="Web team"
  preconditions="Signed out. Login page open at https://staging.example.com/login. Both fields empty."
  testData={`Email: (empty)\nPassword: (empty)`}
  steps={[
    "Open https://staging.example.com/login",
    "Leave the Email field empty",
    "Leave the Password field empty",
    "Click Sign in"
  ]}
  expected="An inline error, 'Email is required', appears under the Email field. No sign-in request is sent."
  actual="A sign-in request is sent (POST /api/session returns 400). A spinner shows for about 2 seconds, then disappears. No error message appears, and the user stays on the login page."
  attachments="Screen recording (12 seconds). Network tab export of the POST /api/session request and its response. Browser console: no errors."
  notes="Happens every time in Chrome (5 of 5 tries). Does not happen in Firefox 159.0, where the error shows correctly. Safari not tested."
/>

Why this example works:

- **The title names the area, the failure and the condition.** A developer scanning the backlog knows what it is without opening it.
- **The steps start from a known state.** The preconditions say signed out and which page, so nobody guesses the starting point.
- **Expected and actual are concrete.** The expected result quotes the message; the actual result includes what the network shows, not only what the screen shows.
- **The notes narrow it down.** "Every time in Chrome, never in Firefox" tells the developer where to look before they open the code.

## Which fields should every bug report include?

Every report needs enough for someone else to reproduce the bug, judge its impact, and later verify the fix. These fields cover that:

| Field | What to write | Example |
|---|---|---|
| Title | Area, what broke, and the condition | Checkout: total shows $0 after applying a coupon |
| Environment | Browser or app version, OS, test environment, build | Chrome 158.0, Windows 11, staging build 2.4.1 |
| Preconditions | The state before step 1 | Signed in as a customer with one item in the cart |
| Test data | The exact values you used | Coupon code SAVE10 |
| Steps | Numbered, one action each | 1. Open the cart. 2. Enter SAVE10. 3. Click Apply |
| Expected result | What the requirement says should happen | Total drops by 10% |
| Actual result | What happened, with exact messages | Total shows $0.00; no error |
| Frequency | Always, sometimes (how often), or once | 3 of 3 tries |
| Severity | Impact on the system | High |
| Priority | Proposed urgency, confirmed in triage | P2 |
| Evidence | Recording, screenshot, logs, network export | Screen recording attached |

## How do you write a bug report title?

Use the pattern **area: what broke + condition**. The title is the most-read part of the report, so it should make sense in a list view with nothing else around it.

**Weak titles:**
- "Login doesn't work"
- "Bug on checkout page"
- "App crashes"

**Strong titles:**
- "Login: form submits with empty email, no validation error (Chrome)"
- "Checkout: order total shows $0 after applying a coupon"
- "Reports: PDF export crashes on reports over 500 rows (Safari)"

## How do you write steps to reproduce?

Write one action per step, in order, from a known starting state, with the exact data you used. The last step is the one where the bug shows. If a step depends on something you did earlier, such as being signed in, move it into the preconditions.

**Weak steps:**
> Go to the cart and apply a coupon. Total is wrong.

**Strong steps:**
> 1. Sign in as `customer.qa@example.com`.
> 2. Add one "Basic plan" to the cart.
> 3. Open the cart.
> 4. Type `SAVE10` into the Coupon field and click **Apply**.

Before you submit, follow your own steps once more, exactly as written. If you cannot reproduce it from the text alone, neither can the developer.

## How do you write the expected and actual results?

State the expected result from the requirement, and the actual result as exactly as you can: quote messages word for word, and include what the network or console shows. Never write "it doesn't work": say what happened instead.

**Weak:**
> Expected: It works.
> Actual: It doesn't work.

**Strong:**
> Expected: Clicking **Place order** shows the toast "Order placed!" and opens `/orders/123` within 2 seconds.
> Actual: Clicking **Place order** shows a spinner for 10 seconds, then a blank page. No toast. The URL stays `/checkout`. `POST /api/orders` returns `500`.

For an API bug, paste the request (method, URL and body) and the response (status and body). If an automated test found it, its failure output is evidence too; see [how to test REST APIs with Playwright in Python](/blog/playwright-api-testing-guide).

## What is the difference between severity and priority?

Severity is how badly the defect affects the system; priority is how soon the team should fix it. They are set separately because they often disagree: a crash in a rarely used screen can be severe but not urgent, and a typo on the home page can be trivial but urgent.

| | Low priority | High priority |
|---|---|---|
| **High severity** | A rarely used admin export crashes, and a workaround exists | Checkout fails for every customer |
| **Low severity** | A typo on an internal settings page | The company name is misspelled on the home page |

Azure DevOps documents the same idea with an example: a rarely used link that crashes a page might get **Severity 2 - High** but **Priority 3**, because the experience is severe but rare ([Microsoft's guide to managing bugs in Azure Boards](https://learn.microsoft.com/en-us/azure/devops/boards/backlogs/manage-bugs?view=azure-devops)). Its four severity levels are a good default if your team has none:

| Severity | Meaning |
|---|---|
| 1 - Critical | A component or the whole system stops, or data is badly corrupted, and there is no workaround |
| 2 - High | The same impact as critical, but an acceptable workaround exists |
| 3 - Medium | The system gives incorrect, incomplete or inconsistent results |
| 4 - Low | A minor or cosmetic problem with an acceptable workaround |

## How do the fields map to Jira and Azure DevOps?

Both tools have a place for every field above, but the names differ, and Jira has no severity field out of the box.

| Bug report field | Jira | Azure DevOps (Bug work item) |
|---|---|---|
| Title | Summary | Title |
| Steps, expected and actual | Description | Repro Steps |
| Environment | Environment, if your project shows it; otherwise the description | System Info |
| Build or version | Affects versions, if your project uses versions | Found In Build |
| Severity | Not there by default: an admin adds it as a custom field | Severity (1 - Critical to 4 - Low) |
| Priority | Priority | Priority (1 is the highest) |
| Evidence | Attachments | Attachments |
| Fixed in | Fix versions | Integrated in Build |

Two notes on these tools:

- **Severity in Jira.** Jira Software projects do not include a Severity field by default, so teams usually add a single-select custom field. Sites that also use Jira Service Management may already have one ([Atlassian Community discussion](https://community.atlassian.com/t5/Jira-questions/Why-there-is-no-Severity-Field-for-Issue-Type-Bug/qaq-p/1117643)).
- **Regressions in Azure DevOps.** Microsoft's guidance is not to reopen a closed bug when the problem comes back, but to open a new bug and link it to the old one with a Related link.

## What evidence should you attach?

Attach at least one piece of evidence, and pick the one that shows the problem fastest:

1. **A screen recording** for anything involving timing, animation or several steps.
2. **A screenshot** with the problem area marked.
3. **The browser console output**, copied in full, not just the first line.
4. **A network export** of the failing request: in DevTools, open the Network tab and save the request and its response.
5. **Server logs**, if you have access, with the timestamp of your test.

<Callout type="warning" title="Clean your evidence before you attach it">
  Screenshots, logs and network exports can contain passwords, session tokens, API keys and customer data. A browser network export (HAR file) includes cookies and authorization headers. Remove or mask them before you attach anything to a ticket.
</Callout>

## How does a bug report become a regression test?

Once the bug is fixed, its steps and expected result are a ready-made test case: run them to verify the fix, then keep them in the regression suite so the bug cannot quietly return.

<TestCase
  id="REG-1042"
  title="Login rejects an empty email field"
  objective="Verify the fix for QA-1042 and guard against a regression"
  preconditions="Signed out, on /login, both fields empty"
  testData={`Email: (empty)\nPassword: (empty)`}
  steps={[
    { action: "Leave the Email field empty", expected: "The field stays empty" },
    { action: "Leave the Password field empty", expected: "The field stays empty" },
    { action: "Click Sign in", expected: "'Email is required' appears under the Email field and no sign-in request is sent" },
  ]}
  priority="high"
  type="Regression"
  author="Dipak Bist"
/>

A check like this runs on every release, so it is a good candidate for automation. To decide case by case, use this [checklist for when to automate a test](/blog/manual-vs-automation-testing).

## Can AI help you write better bug reports?

Yes, for spotting what is missing. An AI tool can point out a vague title, a missing environment or merged steps. It cannot know how your product should behave, so the expected result must come from the requirement, and it should never see real customer data, passwords or internal URLs.
