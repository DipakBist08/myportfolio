Automate a test when it runs often, its steps and expected result are stable, and running it by hand costs more than keeping the automation working. Keep it manual when it needs human judgment, runs once, or covers a feature that is still changing. The checklist below turns that into seven yes-or-no questions you can apply to any single test.

<KeyTakeaways>
- Decide test by test, not with a target percentage.
- Automate checks that repeat, stay stable, and have a result code can verify.
- Keep exploratory, usability and one-off checks manual.
- Automate at the lowest level that can catch the bug: unit or API before the UI.
- Judge automation by the real bugs it catches, not by how many tests exist.
</KeyTakeaways>

## How do you decide whether to automate a test?

Answer these seven questions for the one test in front of you. The first three are must-haves; the rest decide when, and at which level, to automate.

<QAChecklist
  title="Should this test be automated?"
  items={[
    { text: "1. It will run many times: every build, every sprint, or before every release" },
    { text: "2. The same input gives the same result: no human judgment, no randomness" },
    { text: "3. Code can check the expected result: a value, a status, a message, an element" },
    { text: "4. The feature is stable: its flow is signed off and not being redesigned" },
    { text: "5. The test can create and clean up its own data" },
    { text: "6. Over the next few months, running it by hand costs more than building and maintaining it" },
    { text: "7. Someone on the team can fix it when it breaks" },
  ]}
/>

How to read the answers:

- **Yes to all seven:** automate it now.
- **No to question 1, 2 or 3:** keep it manual. Automation will not pay back, or it cannot check the result.
- **Yes to 1 to 3, but no to any of 4 to 7:** automate later, or at a lower level. An API test is often stable while the UI is not.

## How does the checklist work on real tests?

Here are three typical tests run through the checklist:

| Question | Sign in with valid credentials | "Is the new onboarding flow easy to follow?" | Monthly invoice PDF |
|---|---|---|---|
| 1. Runs many times | Yes: every build | Yes: every design change | No: once a month |
| 2. Same input, same result | Yes | No: it is a judgment | Yes for the numbers |
| 3. Code can check the result | Yes: the URL and heading | No | The totals yes, the look no |
| 4. Stable feature | Yes | No: still in design | Yes |
| 5. Creates its own data | Yes: a test account | Not relevant | Yes |
| 6. Cheaper automated | Yes | No | For the totals |
| 7. Someone can maintain it | Yes | Not relevant | Yes |
| **Decision** | **Automate as a UI smoke test** | **Keep manual: usability** | **Automate the totals at API level; check the layout by hand** |

The third column is the common case: one feature, two decisions. Split the test along the line between what code can check and what needs a person.

## What should not be automated?

Keep these manual, or automate only the part that code can check:

- **Exploratory testing.** Its value is in what the tester decides to try next. Write a charter, not a script.
- **Usability, and look and feel.** Code can check that a button exists, not whether people understand it. Visual regression tools catch changes, but a person still decides whether a change is right.
- **One-off checks.** A data migration you run once does not repay the effort of automating it.
- **Features that are still changing.** UI tests written now break with every redesign, for reasons that are not bugs.
- **Flows you cannot make deterministic.** Real payment providers, CAPTCHAs and third-party emails. Test your side of them with stubs at the API level instead.
- **Accessibility, beyond the basics.** Automated scanners catch some problems, such as missing alt text or low contrast, but not whether a screen reader user can finish the task.

The Ministry of Testing community has a long thread on [what should not be automated](https://club.ministryoftesting.com/t/what-should-not-be-automated/43058), with examples from many teams.

## Manual vs automation testing: how do they compare?

Manual testing is a person running the test and judging the result. Automation testing is code running the test and comparing the result with fixed expectations. Each is strong where the other is weak:

| | Manual testing | Automation testing |
|---|---|---|
| Best at | New features, exploring, usability, one-off checks | Regression, smoke tests, many data combinations |
| Finds | New and unexpected problems | Regressions in behavior that is already checked |
| Cost to start | Low | High: writing and debugging the tests |
| Cost to repeat | The same effort every run | Low per run, plus maintenance when the product changes |
| Speed per run | Slow | Fast once built |
| Judgment | Yes | None: only what the code asserts |
| Consistency | Varies between runs and testers | The same steps every run |
| Runs in CI | No | Yes |

## Where should automated tests sit?

As low in the stack as the check allows. The test pyramid describes the balance: many fast unit tests at the base, fewer integration and API tests in the middle, and the fewest end-to-end UI tests at the top, because UI tests are the slowest and break most easily. Martin Fowler's [Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html) explains it with examples, and Google's testing blog argues the same point in [Just Say No to More End-to-End Tests](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html).

In practice:

- **Unit tests**, usually written by developers, check logic and edge cases.
- **API tests** check business rules, permissions and data without a browser. See [how to write Playwright API tests in Python](/blog/playwright-api-testing-guide).
- **UI tests** check the few journeys that only make sense in a browser, such as signing in or checking out.

## What is a good first test to automate?

Signing in with valid credentials passes all seven questions, which makes it a common first UI test. Here it is in Playwright for Python, with its negative twin:

```python title="tests/test_login.py"
import re

from playwright.sync_api import Page, expect


def test_login_with_valid_credentials(page: Page):
    page.goto("/login")

    page.get_by_label("Email").fill("qa.user@example.com")
    page.get_by_label("Password").fill("correct-horse-battery")
    page.get_by_role("button", name="Sign in").click()

    expect(page).to_have_url(re.compile(r"/dashboard$"))
    expect(page.get_by_role("heading", level=1)).to_have_text("Welcome, QA User")


def test_login_with_wrong_password_shows_an_error(page: Page):
    page.goto("/login")

    page.get_by_label("Email").fill("qa.user@example.com")
    page.get_by_label("Password").fill("wrong-password")
    page.get_by_role("button", name="Sign in").click()

    expect(page.get_by_role("alert")).to_have_text("Email or password is incorrect.")
    expect(page).to_have_url(re.compile(r"/login$"))
```

Three things make this test hold up:

- **The locators are what a user sees:** a label, a button name, a heading. They survive markup changes better than CSS selectors; see [Playwright's guide to locators](https://playwright.dev/python/docs/locators).
- **`expect` waits.** Each assertion retries until it passes or times out, so there are no `sleep()` calls. See [Playwright's assertions](https://playwright.dev/python/docs/test-assertions).
- **`page.goto("/login")` is relative.** pytest-playwright passes the `base_url` fixture to every browser context, so the app's address lives in one place.

The tests run against a small local login app that starts with the test session, so they run anywhere. The [login test example project on GitHub](https://github.com/DipakBist08/myportfolio/tree/main/blog/examples/manual-vs-automation-testing) has the app and its `conftest.py`. This is the run for this article:

```text
tests/test_login.py::test_login_with_valid_credentials[chromium] PASSED  [ 50%]
tests/test_login.py::test_login_with_wrong_password_shows_an_error[chromium] PASSED [100%]

============================== 2 passed in 1.21s ===============================
```

Now compare what a manual tester notices on the same screen: an error message that confuses people, a password field that hides the Caps Lock warning, a layout that breaks on a small phone. Neither kind of testing replaces the other.

## How do you know if your test automation is working?

Measure what it catches and what it costs, not how many tests exist:

- **Real bugs caught before release.** If the suite has not caught one in months, it may be checking the wrong things.
- **False failures.** How often does a red build turn out to be a flaky or outdated test? Each one costs a person's time and the team's trust.
- **Run time.** A suite that takes too long stops being run on every change.

A team with 2,000 tests that never catch anything gets less from automation than a team with 50 well-chosen tests that catch real regressions.

## What are the most common automation mistakes?

- **Automating too early.** UI tests for a feature still in design break every sprint. Wait until the flow is signed off, or test the API first.
- **Automating a flaky flow without fixing it.** Flaky tests teach the team to ignore red builds. Fix the test isolation or the timing first.
- **Dropping manual testing entirely.** Automation only checks what you already thought of. Keep exploratory sessions for new features.
- **Putting every check in the UI.** Checks that could run as API tests take longer and break more often as UI tests.
- **Counting tests instead of results.** See the previous section.

When an automated check does catch a real bug, report it so it gets fixed fast; this [bug report example](/blog/how-to-write-good-bug-report) shows what to include.
